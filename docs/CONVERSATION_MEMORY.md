# Conversation Memory Operations

## Scope and identifiers
- A conversation is identified by a random session ID generated by the Streamlit UI.
- The API derives a SHA-256 checkpoint thread key from patient ID plus session ID. Raw patient IDs and session IDs are not used as SQLite thread keys or written to application logs.
- Reusing both identifiers continues the same conversation. A new session ID starts a separate conversation. Changing the patient ID also creates a separate checkpoint namespace.

## Persistence, retention, and deletion
- Checkpoints are stored in `data/conversations.sqlite3` by default; `CHECKPOINT_DB_PATH` can select another path.
- Prototype default: records persist until an operator deletes them; there is no automatic expiration. A clinic operator must establish and communicate a legally appropriate retention period before real patient data is used.
- To delete all conversations, stop the API and remove the configured SQLite database file (and any SQLite `-wal`/`-shm` sidecars). This is a full-store deletion, not per-patient deletion. Do not remove the database while the service is running.
- Back up using SQLite's online backup mechanism or while the API is stopped. Protect backups with access controls and encryption appropriate for patient data; periodically verify restore procedures.

## Concurrency and deployment limits
- The current SQLite saver is intended for a single application process on one host. Do not run multiple API workers/replicas against this SQLite file and assume distributed coordination.
- For multi-process/multi-host production, move checkpoint storage to a supported shared transactional backend and test concurrent writes, backup, restore, and retention before deployment.

## Manual Streamlit acceptance
1. Start API and Streamlit; enter a valid patient ID and ask a question.
2. Ask a follow-up; confirm the transcript remains visible and the backend continues the same session.
3. Select **Start new conversation**; confirm the visible transcript clears and the next message begins a fresh context.
4. Change patient ID while retaining the session; confirm backend checkpoint history is isolated by patient.
5. Restart the API while retaining the same patient ID/session ID; confirm stored context is available.
6. Verify invalid IDs and service failures produce a clear message without exposing internal exception details.
